Pragmatica Aether

Let Java Be Java

Java was designed for managed environments. Applets ran in browsers. Servlets ran in app servers. EJBs ran in containers. The fat-jar era threw that away — we started bundling web servers, serialization, service discovery, and configuration management into every application, then wrapping it all in Docker.

Aether returns Java to its natural habitat. Applications handle business logic. The runtime handles everything else.

The Coupling Trap

Every Java microservice carries a heavy coat of infrastructure: web servers, serialization, DI containers, service discovery, config management, metrics, retry logic, circuit breakers.

Your pom.xml doesn't distinguish business dependencies from infrastructure dependencies. They compile together, deploy together, and break together. A security patch in Netty requires rebuilding every service that embeds a web server — which is all of them.

DI frameworks fight with service meshes for routing control. Cloud SDK retry logic conflicts with application-level resilience libraries. Every layer claims authority over the same cross-cutting concerns, and the conflicts surface as bugs in production — not during development.

The Way Out

This is an architecture problem. Architecture problems have architectural solutions.

Separate the layers. Let the runtime manage infrastructure — resource provisioning, scaling, transport, discovery, retries, circuit breakers, configuration, observability, security. None of these are application concerns.

Update Java — roll it out across nodes without touching applications. Update business logic — deploy new versions without touching infrastructure. Each independently, each without downtime. When layers don't share a deployment unit, they don't share a deployment schedule.

What You Write

A slice is a Java interface — the same mental model as a service. Define methods, declare dependencies, implement business logic. If you've written a Spring service, you can write a slice.

@Slice
public interface OrderService {
    Promise<OrderResult> placeOrder(PlaceOrderRequest request);

    static OrderService orderService(InventoryService inventory,
                                     PricingEngine pricing) {
        return request -> inventory.check(request.items())
                                   .flatMap(available -> pricing.calculate(available))
                                   .map(priced -> OrderResult.placed(priced));
    }
}

What You Don't Write

  • No HTTP clients — inter-slice calls are direct method invocations via generated proxies
  • No service discovery — the runtime tracks where every slice instance lives
  • No retry logic — built-in retry with exponential backoff and node failover
  • No circuit breakers — the reliability fabric handles failure automatically
  • No serialization code — request/response types are serialized transparently
  • No configuration management — consensus-based config propagates cluster-wide

A method call via imported interface is the only visible contract. Not message passing, not actors, not a new programming paradigm — typed Java interfaces with request/response semantics. Your existing service-based designs, interaction patterns, and team knowledge transfer directly. The only design requirement: slice methods should be idempotent — enabling retry, scaling, and fault tolerance to work transparently.

Under The Hood

Ten architectural decisions make this possible.

  • Consensus KV Store. Single source of truth for configuration, deployment state, and service discovery. Based on the Rabia protocol — a leaderless consensus algorithm. Any node can propose. Self-contained — no external coordination services required.
  • Two-Layer Topology. Core nodes run Rabia consensus (3-9 nodes). Worker groups scale independently via SWIM gossip protocol — thousands of nodes, O(1) failure detection, zero consensus overhead. Governors elected deterministically, no election messages. Proven with 12-node Docker scaling test: zero failures, zero SWIM faults.
  • Built-in Artifact Repository. DHT-based storage with configurable replication and integrity verification. In development, slices resolve from your local Maven repository. In production, the cluster stores and distributes artifacts internally.
  • ClassLoader Isolation. Each slice runs in its own classloader with child-first delegation. Two slices can use different versions of the same library without conflict. No dependency conflicts, no classpath hell.
  • Declarative Deployment. Blueprints packaged as deployable JAR artifacts — containing slice configuration, database migration scripts, and application config. Deploy with one command. The cluster resolves artifacts, runs schema migrations, and converges to the desired state automatically.
  • Infrastructure Independence. A single aether-node.jar runs as both core and worker — the node discovers its role from the cluster topology. Node updates, runtime updates, and application deployments run on completely independent schedules.
  • Node Lifecycle Management. Nodes move through JOINING, ON_DUTY, DRAINING, DECOMMISSIONED, SHUTTING_DOWN states. Graceful drain respects disruption budgets. Liveness and readiness probes built in.
  • Native Async Database. Built-in async PostgreSQL driver with binary wire protocol and built-in pipelining — multiple queries in flight per connection without round-trip serialization. No external connection pooler needed — pipelining is handled inside the driver, one fewer component to deploy, configure, and monitor. Three integration paths: direct async (zero adapter overhead), R2DBC adapter, and jOOQ. LISTEN/NOTIFY support for reactive event-driven patterns.
  • Transport Security. Mutual TLS for all node-to-node TCP communication — derived from a shared cluster secret via HKDF, no external PKI required. SWIM gossip encrypted with AES-256-GCM and zero-downtime key rotation.
  • RBAC and Audit. Three hierarchical roles (ADMIN/OPERATOR/VIEWER) with per-route enforcement. SHA-256 hashed API keys, operational audit trail with 7 event types, cluster-wide event aggregation.

The blueprint artifact carries slice configs, database migrations, and application settings. The cluster resolves artifacts, runs schema migrations, loads slices, distributes instances across nodes, registers routes, and starts serving traffic. One artifact, one command.

The 50% Rule

The system survives failure of less than half the core nodes. Not graceful degradation — actual redundancy. A 5-node cluster tolerates 2 simultaneous failures. A 7-node cluster tolerates 3.

When a node fails, recovery is automatic. Requests are immediately retried on healthy nodes. A replacement is provisioned, connects to peers, restores state from a cluster snapshot, and begins serving traffic. No human intervention required.

All inter-node communication secured with mutual TLS derived from a shared cluster secret — no external PKI. SWIM gossip encrypted with AES-256-GCM with zero-downtime key rotation.

Zero-Downtime Updates

Four deployment strategies, built in:

  • Rolling — weighted traffic routing with gradual shift
  • Canary — progressive stages (1% → 5% → 25% → 50% → 100%) with automatic health evaluation and auto-rollback
  • Blue-green — atomic traffic switchover in ~100ms via single consensus round
  • A/B testing — deterministic traffic split by request context with per-variant metrics

Deploy during business hours. If health degrades — instant rollback with one command.

Scaling That Manages Itself

Three Dimensions

Slice scaling — spin up more instances of a specific slice on existing nodes. Classes are already loaded; scaling takes milliseconds.

Node scaling — add more machines to the cluster. The node connects, restores state, and begins accepting work.

Worker group scaling — add worker groups that scale independently via SWIM gossip. Core stays at 5-9 nodes for consensus; workers scale to thousands with zero consensus overhead.

Three Tiers of Intelligence

  • Tier 1 — Decision Tree (1-second intervals). Reactive scaling based on CPU, latency, queue depth, and error rate. Deterministic, fast, always reliable.
  • Tier 2 — TTM Predictor (60-second intervals). ONNX-based ML model analyzing a 2-hour sliding window with 11-metric feature vector. Variance-based confidence scoring. Forecasts load and adjusts thresholds preemptively. Scale before the spike, not after.
  • Tier 3 — LLM-based (planned). Long-term capacity planning, seasonal patterns, anomaly investigation.

If TTM fails, the Decision Tree continues with default thresholds. No scaling disruption.

For Every Project

Slices are services — right-sized, without the infrastructure tax. Your existing service boundaries, API contracts, and domain decomposition apply directly. Legacy and greenfield coexist in the same cluster.

Legacy Migration

Your legacy system doesn't need a rewrite. Pick a boundary, extract an interface, annotate with @Slice, wrap the implementation:

Promise.lift(() -> legacyService.generate(request));

One line to enter the Aether world. Start in Ember — single JVM, same process as your existing application. No worse than what you have today. From there, the strangler fig pattern: extract a hot path, deploy as a slice, route traffic, repeat.

One sprint to first slice in production.

Greenfield

Each slice can be as lean as a single method — and that's the recommended approach. No operational tradeoffs for small slices because Aether handles all infrastructure overhead.

One slice serving 50 instances during peak load while another idles at minimum. That granularity would be operationally insane with traditional microservices. With Aether, it's the default.

JBCT patterns — Leaf, Sequencer, Fork-Join — compose naturally within slices. Each slice method is a data transformation pipeline: parse input, gather data, process, respond.

From Laptop to Production

Three environments, zero code changes.

E

Ember

Embeddable cluster runtime with fluent builder API. Multiple logical nodes in the same JVM. Fast startup, standard debugger. Deploy slices alongside your existing application — the zero-risk entry point for legacy migration.

F

Forge

5-node cluster simulator on your laptop with built-in passive load balancer. Real consensus, real routing, real failure scenarios. Web dashboard with live metrics. Chaos injection — kill nodes, crash leaders, trigger rolling restarts.

A

Aether

Production cluster. Same slices, same code, different scale. Your code doesn't know which environment it's running in. Moving from Ember to Aether is a configuration change, not a code change.

Why BSL?

BSL protects our ability to sustain development while keeping Aether accessible. Large cloud providers can't wrap and sell it, but you can use it freely for your applications.
